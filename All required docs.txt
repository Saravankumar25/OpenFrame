No. **PRD + ESD + README are not enough for 100% product/build coverage.**

They can get you very far, but each answers a different question:

* **PRD:** What are we building and why?
* **ESD:** How will the software technically be structured/built?
* **README:** How does a developer set up, run, understand, and contribute to the project?

The biggest missing piece is usually the exact **behavioral contract between product, design, and engineering**.

For OpenFrame, I would use the following document set.

# The complete documentation stack

# 2. FSD — Functional Specification Document

This is the **biggest missing document**.

Your PRD says:

> "Users can create scene cards."

The FSD says exactly what that means.

For example:

### Create Scene Card

**Entry points**

* Story Board → `+ Scene`
* Sequence context menu → `Add Scene`
* Keyboard shortcut
* Convert Beat → Scene

**Default fields**

* Description
* Optional scene heading

**On creation**

1. New scene receives unique internal identity.
2. Scene appears at the end of the selected sequence.
3. Card becomes selected.
4. Description field receives focus.
5. User can immediately type.
6. Scene number is not stored as a user-entered value.
7. Displayed numbering is calculated from current order.

**On drag**

* Parent sequence changes if moved between sequences.
* Ordering updates.
* Displayed numbering updates.
* Existing screenplay relationship remains attached to the same scene identity.

**On duplicate**

* New scene identity.
* Content copied.
* Production associations copied or not copied according to defined rules.

**On delete**

* Confirmation rules.
* Undo behavior.
* What happens to screenplay scene?
* What happens to breakdown?
* What happens to comments?

That's the level your engineers actually need.

### The FSD should contain every feature.

Not just major modules.

# 5. Data / Domain Model Specification

This is extremely important for OpenFrame.

Your application is fundamentally a network of relationships.

For example:

```text
PROJECT
 ├── IDEA
 ├── STORY BOARD
 │    ├── ACT
 │    │    └── SEQUENCE
 │    │         ├── BEAT
 │    │         └── SCENE
 │    └── CHARACTER
 │
 ├── SCREENPLAY
 │    └── SCREENPLAY SCENE
 │
 ├── BREAKDOWN
 │    └── PRODUCTION ELEMENT
 │
 ├── LOCATION
 ├── CAST
 ├── PROP
 ├── SHOT
 ├── SHOOTING DAY
 └── CALL SHEET
```

The domain document defines:

> What is a Scene?

> What is an Idea?

> What is a Draft?

> What is a Character?

> What is a Shooting Day?

and:

> How exactly are they related?

This is critical because otherwise two engineers can interpret the same relationship differently.

# 6. Collaboration & Offline Specification

Because you specifically decided:

> **No cloud dependency + desktop-first + offline**

this deserves its own document.

It should define three separate workflows:

### Mode 1 — Solo

Everything works locally.

### Mode 2 — Portable exchange

Example:

```text
Writer A
   ↓
Export Review Package
   ↓
Send file
   ↓
Writer B
   ↓
Open package
   ↓
Add comments/changes
   ↓
Export Response Package
   ↓
Writer A
   ↓
Import / Review / Merge
```

### Mode 3 — Local-network collaboration

Example:

```text
Computer A
Project Host
    ↕
Local Network
    ↕
Computer B
    ↕
Computer C
```

The specification needs exact rules for:

* simultaneous editing
* conflict handling
* project ownership
* merge
* comments
* file versions
* offline edits
* reconnection
* interrupted transfers
* package compatibility

Without this document, engineers will invent their own collaboration model.

# 8. AI Specification

Since you want an AI assistant similar in spirit to Amazon Q, don't bury this inside the PRD.

Create:

# OpenFrame AI Specification

It should define:

### AI can

* Search project information
* Summarize
* Explain
* Find relevant scenes
* Identify likely breakdown elements
* Create suggested scene cards
* Transform rough notes into structured notes
* Help create production documents
* Answer questions about the current project

### AI cannot

* silently change the screenplay
* silently delete information
* silently reorder the story
* silently alter production data

Every AI-generated modification should have:

> **Review → Accept / Reject**

That distinction is extremely important.

# 9. QA / Acceptance Specification

This is what turns:

> "I think this feature works"

into:

> "We have objectively verified this feature."

For every feature:

```text
Feature
↓
Scenario
↓
Action
↓
Expected Result
```

Example:

### Scene reorder

**Given**

Scene 4 is before Scene 5.

**When**

User drags Scene 5 before Scene 4.

**Then**

Scene order becomes 1,2,3,5,4.

**And**

Screenplay order reflects the new order if the scene is linked.

**And**

Scene identities remain unchanged.

**And**

Breakdown relationships remain attached.

**And**

Undo restores the original state.

That becomes an automated/manual test case.

# 11. Version / Migration Specification

This is often forgotten.

Suppose OpenFrame 1.0 creates:

> `Project A`

Then OpenFrame 2.0 changes the project format.

What happens?

You need rules for:

```text
Project v1
 ↓
OpenFrame v2
 ↓
Migration
 ↓
Project v2
```

Also:

> Can an old project be opened?

> Is it upgraded automatically?

> Can it be backed up first?

> Can users downgrade?

> What happens if an import fails?

This becomes essential once real filmmakers store years of work in the application.

# 12. README

README is actually the **least important** of these from a product-definition perspective.

It should mainly tell developers:

> Install dependencies.

> Run application.

> Run tests.

> Build desktop package.

> Project structure.

> Development commands.

> Contribution rules.

> Branch/commit standards.

It should **not** be the place where product behavior is specified.

# Can you achieve literally "100%" coverage?

Not literally.

No document set can eliminate every engineering question.

During implementation, engineers will encounter unforeseen cases.

What you **can** achieve is:

> **100% planned product coverage before development begins.**

For OpenFrame I'd define that as:

### Product coverage

Every intended feature has a specification.

### Interaction coverage

Every major user action has defined behavior.

### State coverage

Every important object has lifecycle/state rules.

### Relationship coverage

Every connection between modules is defined.

### Failure coverage

Important errors and edge cases have defined responses.

### Data coverage

Every persistent object has defined fields/relationships.

### Import/export coverage

Supported formats have explicit rules.

### Collaboration coverage

Offline/local-network/portable workflows have defined rules.

### QA coverage

Every requirement has acceptance tests.

Once those are covered, your engineering team can make implementation decisions without repeatedly coming back to you asking:

> "What did you mean by this?"
