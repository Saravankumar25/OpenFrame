# 4. System design assessment

## 4.1 Overall architecture

The core dependency direction is sound:

```text
React / TypeScript UI
        |
        v
Tauri adapter / IPC
        |
        v
openframe-application
        |
        +--> Registry / authorization
        |
        +--> domain modules
        |
        +--> single Store mutation pipeline
        |
        v
openframe-persistence
        |
        v
SQLite canonical project state
```

AI follows a similarly constrained path:

```text
User
 |
 v
Bounded local agent
 |
 +--> retrieval / read / compute
 |
 +--> proposal tools
 |
 v
Change Set draft
 |
 v
Human review
 |
 v
normal Registry commands
 |
 v
Store mutation pipeline
 |
 v
SQLite
```

This is the correct basic architecture for the product's stated goals.

## 4.2 Strong architectural decisions

### React is presentation, not the source of truth

The webview does not directly own the database or filesystem.

That avoids a common Tauri/Electron anti-pattern where business logic becomes scattered across the frontend.

### Tauri is treated as an adapter

`apps/desktop/src-tauri/src/lib.rs` explicitly behaves as a boundary layer rather than becoming the application itself.

That is good separation of concerns.

### One controlled mutation pipeline

Persistent canonical writes pass through `Store::mutate`.

The design performs:

```text
permission
-> BEGIN IMMEDIATE transaction
-> domain mutation
-> undo capture
-> search reindex
-> activity
-> commit
-> observer/events
```

This is one of the strongest parts of the repository.

### Operation Registry is a meaningful application boundary

Commands/queries are registered and increasingly carry metadata such as:

- capability;
- AI exposure;
- operation class;
- destructive status;
- filesystem effects;
- confirmation needs.

That metadata is useful for:

- authorization;
- AI safety;
- auditing;
- future tooling;
- maintaining a single behavioral contract.

### AI authority is explicitly below human authority

The architecture does not make the model a privileged backdoor.

AI operates under the current user's authority and cannot directly write SQLite.

This is exactly the right design.

# 9. Concurrency and race-condition audit

## 9.1 Strong protections

### Canonical writer serialization

The project Store holds a writer mutex.

Mutations use an immediate SQLite transaction.

This substantially simplifies correctness.

### Separate read path

A query-only read connection is separate from the canonical writer.

This avoids accidentally turning reads into writes and allows SQLite WAL behavior to do its job.

### Observer after commit

The writer lock is released before external observer work is notified.

The CommitObserver contract explicitly says it must enqueue only and not touch the canonical writer.

This is important because it reduces deadlock/reentrancy risks.

### AI Change Set double-accept race

Acceptance performs a compare-and-set update:

```text
Pending -> Accepted
```

and requires exactly one row to be claimed.

That is the correct defense against double-click/two-window acceptance.

### Intelligence invalidation coalescing

The semantic index queue coalesces changes and debounces rapid editing.

That is appropriate for a screenplay editor.

### Sidecar request state

The AI runtime uses a mutex/condition-variable state machine and a BusyGuard with saturating decrement.

This is considerably safer than ad-hoc child-process management.

# 10. Important concurrency / crash-consistency gaps

These do not mean the design is bad. They are the remaining areas I would harden before calling it production-grade.

## P0/P1: multi-operation AI Change Set is not one crash-atomic transaction

A Change Set can contain several ordinary Registry commands.

The application:

1. marks the Change Set Accepted;
2. dispatches each command separately;
3. if one command fails, runs Undo for the commands already applied;
4. finally records the Change Set as Applied.

This gives good logical rollback when the process remains alive.

It does **not** provide true crash atomicity.

Example:

```text
operation 1 commits
operation 2 commits
PROCESS IS KILLED / POWER FAILS
operation 3 never runs
```

After restart, operations 1 and 2 may remain committed while the Change Set is still `Accepted`.

The runtime never got the opportunity to execute compensating Undo.

### Recommendation

Add a durable AI-apply recovery protocol.

Possible approaches:

**Preferred design:**

- persist an apply journal / batch id;
- record each operation boundary;
- on startup, detect `Accepted` but not terminal Change Sets;
- deterministically either:
  - continue applying from a safe point, or
  - compensate already-applied operations;
- test forced process termination after every operation boundary.

For commands that can truly share one transaction, a batch-transaction API would be even stronger, but filesystem-affecting commands make universal single-transaction batching difficult.

This is the most important race/crash gap I found in the new AI write path.

## P1: loopback free-port TOCTOU race

The sidecar manager obtains a free port by:

```text
bind 127.0.0.1:0
-> read chosen port
-> release listener
-> start llama-server on that port
```

Another local process could claim the port during the gap.

This is usually only a reliability race, not a privilege escalation, because the sidecar also uses a random API key.

Still, test this path and ensure startup automatically retries on bind failure.

## P1: background intelligence worker shutdown can detach after timeout

The ProjectIndex shutdown waits up to 20 seconds.

If the worker does not finish, shutdown logs a warning and leaves the thread to exit later.

That is a pragmatic choice, but it creates edge cases around:

- closing and immediately reopening the same project;
- deleting/rebuilding `intelligence.sqlite`;
- app shutdown during a stalled embedding operation;
- file handles remaining open longer than expected.

Add stress tests around repeated open/close/rebuild while the embedding runtime is stalled.

## P1: race/soak validation is not a CI gate

The architecture contains concurrency defenses, but the current CI evidence does not show a dedicated long-running stress suite for:

- concurrent IPC calls;
- rapid autosave;
- undo during background indexing;
- close/reopen while indexing;
- repeated AI request cancellation;
- model process crash/restart loops;
- forced application termination during Change Set application.

This is where production bugs often survive otherwise excellent unit tests.

# 12. Offline AI runtime security

The sidecar design is strong:

- `127.0.0.1`, not `0.0.0.0`;
- random port;
- random 32-byte per-launch API key;
- API key in environment, not command line;
- no web UI;
- offline mode;
- managed lifecycle;
- kill-on-close Windows Job Object;
- no project filesystem authority granted directly to the model server.

This dramatically reduces attack surface.

The downloaded components are protected by:

- signed manifest infrastructure;
- exact bytes;
- hashes;
- HTTPS;
- quarantine on mismatch;
- release gate preventing use of the development signing key.

## Store certification risk: downloaded runtime executable

OpenFrame currently plans to download `llama.cpp` runtime binaries after installation.

Microsoft Store policy permits user-consented add-ons/extensions that enhance the product and prohibits undisclosed dynamic code that fundamentally changes the product.

OpenFrame's design is defensible because Offline AI is:

- user initiated;
- explicitly part of described functionality;
- optional;
- cryptographically verified;
- not a driver/service;
- local.

However, downloading and launching executable code is inherently more certification-sensitive than downloading model weights.

### Safer Store architecture

For the Store channel, strongly consider:

- package the tested `llama.cpp` executable inside the MSIX;
- download only GGUF model/embedding weights after user consent.

Benefits:

- Store scans the executable during certification;
- fewer dynamic-code questions;
- simpler runtime provenance;
- fewer Smart App Control / Windows S-mode surprises;
- runtime version upgrades happen through the Store package.

This is not necessarily required, but it would reduce certification risk.

# 19. Store-specific certification risk: dynamic AI runtime

The repository's own Store engineering document correctly identifies the issue.

OpenFrame downloads:

- model weights;
- embedding weights;
- llama.cpp runtime executable.

Current Store policy allows user-consented add-ons/extensions that enhance disclosed product functionality and prohibits undisclosed dynamic code that changes the product's described behavior.

This may pass certification, but it is a reviewer-sensitive path.

### Strong recommendation

For Microsoft Store builds:

```text
MSIX contains:
  openframe-desktop.exe
  tested llama.cpp runtime

user downloads:
  Gemma weights
  embedding weights
```

rather than downloading the runtime executable.

This reduces:

- certification ambiguity;
- runtime tampering surface;
- executable provenance questions;
- app-control problems;
- runtime/version mismatch.

# 29. Final conclusion

## Does OpenFrame have proper system design?

**Yes.**

The repository has a coherent, defensible system architecture.

Its strongest design choices are:

- Rust owns canonical behavior;
- SQLite is the only project source of truth;
- mutations use a single application pipeline;
- React is not trusted with storage privileges;
- AI cannot directly modify the project;
- derived AI data can be destroyed/rebuilt;
- background indexing does not block canonical saves;
- local AI processes are isolated behind loopback + per-launch authentication;
- release requirements are codified as fail-closed checks.

This is real system design.

## Is OpenFrame AI slop?

**No.**

It is much closer to:

> **AI-assisted, high-volume engineering with strong architectural discipline but insufficient independent stabilization for the size of the newest change.**

That is an important distinction.

## Does it handle edge cases and breakages?

**Yes, substantially.**

It handles many more failure cases than the average pre-release desktop app.

But several production-level cases still need proof through forced-failure and packaged-app testing.

## Does it handle racing conditions?

**Many of the important ones, yes.**

The writer serialization, immediate transactions, Change Set compare-and-set, post-commit indexing, coalescing and sidecar synchronization are good.

The largest remaining correctness concern is the lack of crash-atomic semantics for a multi-command AI Change Set.

## Is it ready for Microsoft Store production?

**No.**

The current codebase is a **strong pre-release foundation**, not a Store-ready final product.

The biggest reasons are not “bad code.”

They are:

1. incomplete product scope;
2. listing/implementation mismatch;
3. unresolved release/legal/configuration blockers;
4. failing supply-chain gate;
5. no WACK evidence;
6. no installed MSIX RC evidence;
7. no AI retrieval/hardware production benchmark;
8. one important Change Set crash-consistency gap.

If those are resolved without degrading the current architectural boundaries, OpenFrame has a credible path to becoming a professionally engineered Store application.
