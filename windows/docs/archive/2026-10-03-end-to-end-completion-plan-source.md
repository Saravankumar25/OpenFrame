# OpenFrame Studio — End-to-End Completion, Integration, AI Enablement & Release Plan

**Status:** Execution master plan
**Prepared:** 2026-10-03
**Repository baseline:** `Saravankumar25/OpenFrame` → `main` → `d30b5889ab5edf9f69d60f8e6d600cb11d4921a0`
**Primary requirements:** supplied `OpenFrame_Manual_vs_GitHub_Audit(1).md` + supplied `OpenFrame_New_Spec_Revised.md`
**Goal:** turn the current OpenFrame codebase into a coherent, production-ready, end-to-end desktop filmmaking application without destabilising the durable core, while integrating the revised screenplay/indie-production requirements and the new appearance/theme system, and making the local AI understand and operate the expanded product safely.

---

## 0. Executive decision

### The correct strategy is **parallel, but dependency-aware**

Do **not** choose either of these extremes:

```text
Wrong strategy A
Finish every remaining manual item
        ↓
Then redesign everything for the new specification
        ↓
Then add AI support
        ↓
Then test everything
```

or:

```text
Wrong strategy B
Build every old feature + every new feature simultaneously
with no contract boundaries
        ↓
Schema churn
UI rewrites
AI/tool mismatches
regressions
unreachable features
```

Use this instead:

```text
                         ┌───────────────────────────────┐
                         │ Durable OpenFrame foundation  │
                         │ Registry / Store / IPC / DB   │
                         │ Undo / Recovery / Security    │
                         └──────────────┬────────────────┘
                                        │
                    ┌───────────────────┼───────────────────┐
                    │                   │                   │
                    ▼                   ▼                   ▼
           DOMAIN WORKSTREAMS      ORTHOGONAL WORK      AI WORKSTREAM
           Old + New combined      Themes / UX /        Tools / RAG /
           by the same module      proofing / outputs   evaluation
                    │                   │                   │
                    └───────────────────┼───────────────────┘
                                        ▼
                              RELEASE / E2E / MIGRATION
                                        │
                                        ▼
                                  SHIPPABLE PRODUCT
```

The central rule is:

> **When a new requirement belongs to a module that is already on the manual completion path, implement the old requirement and the new requirement as one reconciled module contract. Do not build the “old version” and then rebuild it.**

Examples:

- The manual needs a screenplay editor; the revised spec needs professional pagination, continuation, custom elements, Smart structural suggestions, title pages, scene numbering and stronger FDX round-tripping. These are **one screenplay-engine program**, not two projects.
- The manual needs a Schedule; the revised spec adds day timelines, travel/company moves, availability warnings, filters and DOOD. Build the schedule model once with the complete intended data contract.
- The manual needs Call Sheets; the revised spec expands their production information. Design the call-sheet source/snapshot model once, then implement progressively.
- Theme/Appearance is orthogonal to content semantics, so it can proceed in parallel behind the UI token boundary.
- AI should be integrated continuously with new feature operations rather than bolted on after all domain modules are finished.

# 3. The completion model: six states, not one checkbox

Every requirement in the master ledger must move through these states:

```text
S0 — SPECIFIED
Requirement is explicitly identified, with source references.

S1 — CONTRACTED
Domain/data/IPC/command/query and UI route are defined.

S2 — IMPLEMENTED
Real backend + UI code exists and compiles/tests locally.

S3 — REACHABLE
A real user can discover and use it from the product UI.

S4 — VERIFIED
Persistence, undo/recovery, permissions, exports, restart, failure paths and E2E are proven.

S5 — RELEASE-READY
All applicable performance/security/install/migration/documentation gates are green.
```

A feature that is only S2 is **not complete**.

A feature that is S2 + a hidden test is **not complete**.

A feature that has a UI button but no working route is **not complete**.

A feature that works but cannot survive restart is **not complete**.

A feature that can be exported but silently drops structure is **not complete**.

A feature that the AI can mention but cannot safely access through bounded tools is **not complete for AI**.

# 5. Freeze the architecture before adding more feature code

## 5.1 Protect these invariants

The current `CONTRIBUTING.md` invariants should be treated as non-negotiable:

1. React never writes SQLite directly.
2. AI never writes SQLite or arbitrary project files directly.
3. Every persistent mutation is a Rust application command.
4. Every command mutation runs through the transaction pipeline.
5. Stable opaque IDs remain identity; display numbers are not identity.
6. Imports are validated/previewed before changes are applied.
7. Historical snapshots/exports are immutable.
8. LAN collaboration is removed; do not reintroduce listeners.
9. Core works without cloud/accounts/network services.
10. AI failure must not block core editing.
11. WAL/atomic writes/backups/recovery markers remain intact.

Do not accept a feature PR that bypasses one of these constraints to “get it working faster.”

## 5.2 Do not rewrite the Registry/Store/IPC stack to add features

Future changes should follow:

```text
UI intent
   ↓
`call("module.operation", args)`
   ↓
Tauri `of_invoke`
   ↓
Registry allow-list
   ↓
actor/permission validation
   ↓
module handler
   ↓
Store::mutate (if canonical mutation)
   ↓
transaction + undo + activity + reindex + event
```

The existence of this pipeline is precisely why new features can be blended without destabilising the ecosystem.

# 9. Branching and change-isolation strategy

## 9.1 Main branch rule

`main` should remain buildable and testable.

Use bounded feature branches such as:

```text
feat/screenplay-engine
feat/story-card-display
feat/schedule-timeline
feat/callsheet-depth
feat/theme-system
feat/fdx-roundtrip
feat/ai-evals
chore/release-hardening
```

## 9.2 One branch may touch multiple layers, but one feature boundary

A good PR can contain:

```text
screenplay pagination
+ migration
+ operation metadata
+ UI wiring
+ AI read/proposal integration
+ tests
```

A bad PR contains:

```text
screenplay pagination
+ theme refactor
+ installer rewrite
+ unrelated cleanup
+ LAN code deletion
+ new dependency migration
```

Unrelated refactors increase regression risk.

## 9.3 Avoid broad “cleanup” during feature implementation

Do not combine:

- file renaming
- framework migration
- CSS rewrite
- dependency replacement
- database redesign

with a feature unless that change is required by the feature contract.

The safest completion strategy is **small semantic change, large verification**, not **large refactor, then hope**.

# 10. Database and migration policy

The current project migration sequence reaches project migration 0010, while app/global migrations are separate.

## 10.1 Never edit a migration that already exists on main

Do not change:

```text
migrations/project/0001_...
...
migrations/project/0010_...
```

once the migration is part of a shared release lineage.

Add a new migration.

## 10.2 Future schema changes must be backward-safe

Prefer:

```text
new nullable column / new table
      ↓
code reads both old + new where needed
      ↓
backfill
      ↓
validation becomes strict
```

over:

```text
rename/delete old schema
      ↓
old projects break
```

## 10.3 Do not pre-number parallel branch migrations and then guess merge order

Migration ordering is a release artifact. Coordinate the final sequence on main.

A parallel feature branch can carry a migration placeholder in development, but the merged sequence must be linear and deterministic.

## 10.4 Every migration must prove

- fresh database creation
- upgrade from prior supported version
- upgrade with existing data
- safety backup before migration where required
- atomic failure behavior
- reopen after migration
- no accidental data loss
- correct `openframe` schema version
- compatibility with exports/backups where applicable

## 10.5 Themes should use app-local persistence

The revised theme specification explicitly treats appearance preferences as application/user state, not project content.

Therefore:

```text
app.sqlite
   └── appearance preferences

project.sqlite
   └── screenplay / story / production truth

cache/intelligence.sqlite
   └── AI-derived index only
```

Do not put user theme preference into every `.openframe` project.

# 12. The most important integration rule: build a superset contract, not a minimum contract

For each module, first define the **final intended internal shape** from both the old manual and revised spec.

Then implement the simplest usable subset without changing the shape later.

Example — Schedule:

### Bad

```text
schedule row
- sceneId
- day
```

Then later:

```text
ALTER TABLE
add startTime
add duration
add moveType
add availability
add warnings
add DOOD
```

### Better

Design the schedule source model from the revised requirements:

```text
ShootingDay
  ├── date
  ├── sequence/order
  ├── call time
  ├── target wrap
  └── day state

ScheduleItem
  ├── type: Scene | Travel | CompanyMove | MealBreak | CustomBreak
  ├── sceneId?
  ├── startTime?
  ├── durationMinutes?
  ├── locationId?
  ├── castIds[]
  ├── estimate/source metadata
  └── stale/review state
```

Then expose the initial UI gradually.

The same approach applies to screenplay, call sheets and breakdown.

# 27. AI architecture — current state and the correct way to “train it”

## 27.1 Important clarification

The safest interpretation of “train the AI model on the new features” is **not** “immediately fine-tune the Gemma weights.”

OpenFrame’s current AI design is an application-control system:

```text
local model
   +
product tools
   +
retrieval
   +
product knowledge
   +
strict schemas
   +
Change Sets
   +
human approval
```

For an application like OpenFrame, exact feature control is usually achieved more reliably by teaching the model **what tools exist, what they return, what they may mutate, and what product concepts mean**, rather than immediately changing model weights.

Fine-tuning should be a measured later decision, not the default implementation mechanism.

## 27.2 Current AI architecture to preserve

Current architecture includes:

- one production profile
- Gemma 3 1B Instruct
- BGE small English embeddings
- OpenFrame-managed llama.cpp
- hybrid retrieval
- sqlite-vec
- FTS5
- context graph
- bounded agent loop
- universal toolbox
- Change Set review/apply
- provenance
- human-only apply
- no direct SQLite or arbitrary filesystem authority

Do not replace this architecture with a multi-agent framework.

The current AI spec explicitly avoids CrewAI/LangGraph/AutoGen-style swarm architecture.

## 27.3 The right integration pipeline for every new feature

For each new canonical feature:

```text
1. Add domain data / command / query
        ↓
2. Register operation
        ↓
3. Add OperationMetadata
        ↓
4. Decide AI exposure explicitly
        ↓
5. Add bounded read tool
        ↓
6. Add proposal tool where mutation is useful
        ↓
7. Add deterministic entity/reference resolution
        ↓
8. Add document/index projection
        ↓
9. Add graph relationships if useful
        ↓
10. Add product-help knowledge if user questions require it
        ↓
11. Add AI evaluation cases
        ↓
12. Regenerate `ai-tool-coverage.md`
        ↓
13. Run toolbox/security/agent tests
```

This is the key mechanism that lets the AI “learn” the new feature without disturbing the core architecture.

# 44. How to prevent one feature from breaking another

## Rule 1 — Stable IDs everywhere

Never link objects using human display strings.

## Rule 2 — Explicit source relationships

Examples:

```text
CallSheet.sourceShootingDayId
ScheduleItem.sceneId
BreakdownElement.sourceSceneId
Storyboard.sceneId
```

## Rule 3 — Snapshot vs live-source distinction

A call sheet can be an editable/finalized document derived from a schedule snapshot.

A production report can be derived/read-only.

A template copy is independent from the source template.

An AI retrieval index is derived/rebuildable.

Keep these meanings explicit.

## Rule 4 — Stale detection is preferable to silent mutation

When upstream data changes:

```text
Source changed
↓
mark stale
↓
show preview
↓
human chooses update
```

## Rule 5 — No cross-module direct SQL

A module should call its own canonical APIs/queries or explicitly defined application services, not reach into arbitrary other module tables.

If cross-domain data is necessary for a feature, define a typed read model/service.

# 64. Final answer to the sequencing question

The answer is:

> **Build the remaining manual features and the revised-spec additions in parallel, but merge them at the domain/contract level rather than treating them as two independent feature lists.**

Use this rule:

```text
Same module + same data
      ↓
ONE implementation
that satisfies BOTH old + new requirements
```

```text
Different module + low coupling
      ↓
PARALLEL implementation
behind stable interfaces
```

```text
AI
      ↓
CONTINUOUS integration
as soon as each operation is stable
```

This is the approach that minimizes:

- repeated migrations
- duplicate UI work
- duplicated tests
- AI re-integration churn
- cross-module regressions
- unreachable features
- stale documentation

and maximizes the chance of arriving at one coherent product rather than a collection of separately “implemented” modules.

# 65. Final product philosophy

OpenFrame should not become a copy of Final Draft, Word, a studio ERP, or a multi-agent AI platform.

The revised product target is:

> **Professional screenplay depth + simple writing surface + end-to-end indie filmmaking workflow + reliable interchange + local ownership + safe AI.**

The implementation target is therefore not the largest possible feature count.

It is:

```text
Every important feature exists.
Every important feature is reachable.
Every important feature has a canonical source of truth.
Every mutation is safe and undoable where promised.
Every export preserves intended meaning.
Every import reports what it cannot preserve.
Every AI action is permission-bounded and human-approved.
Every theme is presentation-only.
Every release path is tested.
Every previously working area is protected by regression evidence.
```

That is the path from the current OpenFrame repository to a complete software product without unnecessarily disturbing the ecosystem that is already working.

# Appendix D — Closing implementation principle

Every implementation decision should answer one question:

> **Does this make OpenFrame more complete without making its architecture harder to reason about?**

The safest answer will usually be:

```text
reuse the existing command path
reuse the existing data authority
add a narrow typed contract
add the UI route
add the AI metadata/tool if useful
add the tests
```

not:

```text
create a new subsystem
create a second database
create a special AI path
create a new UI navigation model
create a second undo mechanism
create a special export path
```

That discipline is what allows the remaining manual scope and the revised 2026-10-02 specification to become one coherent OpenFrame rather than a collection of incompatible generations of the product.
