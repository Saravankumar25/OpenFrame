# ADR-0013: One local model (Gemma 3 1B), local embeddings, hybrid retrieval with a derived context graph, a universal toolbox and a bounded agent loop

- **Status:** Accepted and implemented (merged on `master`, 30 Sept 2026). **Supersedes ADR-0006 decision 3**
  (the three Qwen profiles and the user override). The rest of ADR-0006 (managed `llama.cpp` sidecar, signed
  manifest, authority boundary, prompt-injection boundary, persistence, failure isolation) stays in force and is
  extended here.
- **Date:** 2026-09-30
- **Related:** `openframe_ai_agentic_rag_spec_prompt.md` (the agentic AI + hybrid RAG spec);
  `OpenFrame_Studio_AI_Specification_Updated.md`; `OpenFrame_Local_AI_Runtime_Model_Management_Specification.md`;
  `docs/engineering/16-search.md`, `18-retrieval-intelligence-index.md`, `ai-tool-coverage.md`; ADR-0004 (single
  dispatcher), ADR-0005 (generic undo), ADR-0009 (permissions), ADR-0012 §5 (no external AI).

## Context

The first AI design (ADR-0006) offered three hardware-picked Qwen profiles and a one-tool orchestrator: the model chose
one tool per request, a hand-built context budget supplied the scope, and search was FTS5 only. The product owner asked
for (1) no model-choice complexity at all, (2) an assistant that can reach every meaningful product action, and (3)
better context for meaning-based questions, while keeping the hard rules: local only, no auto-apply, AI authority never
above the user's.

## Decision

1. **One model, one profile.** Offline AI has exactly one production profile, internal id `openframe-local-ai-v1`:
   Google **Gemma 3 1B Instruct** (GGUF Q8_0, chosen by a benchmark on the real runtime path; runtime spec §4) plus the
   **BGE small English v1.5** embedding model (MIT, 384 dimensions), both served by pinned `llama.cpp` `llama-server`
   sidecars on 127.0.0.1. There is no model picker and no user-loaded model. The manifest format 2 describes runtime +
   chat model + embedding model; format 1 (the Qwen tiers) is refused.
2. **One download.** **Download Offline AI** fetches the runtime and both models as one combined, resumable,
   SHA-256-verified download from the signed manifest, activates atomically, health-checks both sidecars and is usable
   without a restart. Components are stored once per Windows user, never per project.
3. **Derived intelligence index.** Each project gets `cache/intelligence.sqlite` (crate `openframe-search`): semantic
   documents and domain-aware chunks, a `sqlite-vec` `vec0` vector table (statically linked, registered only on
   intelligence connections, no runtime extension loading) and a context graph (`context_node` / `context_edge`,
   provenance Canonical or Derived; Inferred is never produced). It is never canonical, never in undo/activity, not
   needed to open a project, and is deleted and rebuilt on damage, identity or version mismatch. Indexing runs after
   commit on a background worker and never holds the writer transaction.
4. **Hybrid retrieval.** A deterministic router picks Structured / Lexical / Semantic / Hybrid / HybridGraph /
   ProductHelp. Lexical = the canonical FTS5 index; semantic = query embedding + KNN; graph = bounded 1–2 hop expansion.
   Results are merged with Reciprocal Rank Fusion plus scope, exact-name, graph and current-draft boosts (no LLM
   reranker). Every selected item is rebuilt from canonical rows before it reaches the model, so the index can change
   which objects are considered but never their content or visibility. Fallback: hybrid → FTS + SQL → SQL + explicit
   scope.
5. **Universal toolbox from explicit metadata.** Every registered operation carries `OperationMetadata` (module,
   description, AI exposure, class, capability, destructive, irreversible, extra confirmation, filesystem effect,
   long-running). The model sees domain-named tools, never raw operations: bounded read/compute/navigate tools and
   proposal tools. Proposal tools only build a `ChangeSetDraft`; nothing is dispatched while planning. Operations that
   are hidden from the assistant carry a published reason (`docs/engineering/ai-tool-coverage.md`, generated by a test).
6. **One bounded agent, no swarm.** A single loop (default 8 steps, hard cap 12) makes one grammar-constrained model
   call per step to choose the next tool or `final_answer`; stops on repeated identical calls, terminal tools, errors or
   the cap; offers only core tools plus request-relevant tools within a 7,000-character catalogue budget; feeds tool
   results back inside an untrusted-data boundary; persists per-step audit rows (tool, arguments, targets,
   provenance, status) and no reasoning text. Rust validation is the critic; there is no second model.
7. **Human-only approval.** A request that changes the project ends in one composite Change Set (at most 6 parts).
   Accept, reject and re-check are refused for any actor whose origin is not the local user acting in the UI;
   `ai.*` operations can never be inside a Change Set; the operations of an accepted Change Set run through
   `AppCore::dispatch` as ordinary commands (permissions, validation, undo, activity, search), all-or-nothing, grouped
   as one undo step. There is no auto mode, no "always allow" and no remembered approval.
8. **AI authority ≤ user authority.** Every tool runs as the requesting user; private notes are visible only to their
   owner in documents, retrieval, tools and provenance; the permission check is repeated at apply time.

## Consequences

- The Offline AI download is 1,125,156,323 bytes on a processor-only computer (runtime 19.2 MB + Gemma 1,069.3 MB +
  BGE 36.7 MB), instead of the 1–5 GB range of the tiered design.
- A 1B model choosing among many tools in one shot is weak (≈39% tool + argument accuracy in the benchmark). Exact
  facts therefore come from deterministic tools, the catalogue offered per request is small and route-relevant, and
  every model reply is schema-constrained (100% valid JSON in the benchmark).
- Gemma is distributed under the Gemma Terms of Use: the notice is shown in Settings → Offline AI → Technical details
  and in `THIRD_PARTY_LICENSES.md`, and redistribution through the OpenFrame endpoint must pass the terms on (release
  prerequisite, 23-release-migration.md §7).
- Retrieval quality has not yet been measured against an evaluation set (Recall@K / MRR, spec §35); only the
  latency budgets (spec §34) are measured. Until that harness exists, the claim is limited to what the tests show.
- Long-running operations (imports, exports, packages, index rebuild) are hidden from the model today, so no tool
  starts a background task, although the loop handles a task id if one is returned.

## Alternatives rejected

| Alternative | Reason |
|---|---|
| Keep three model tiers / a model picker | Product decision: no model-choice complexity; one tested profile is easier to support |
| Cloud AI, API keys, Ollama | Locked decision (ADR-0006, ADR-0012 §5); project data must not leave the device |
| Neo4j, Qdrant, pgvector or another vector/graph server | Second source of truth, a daemon, and network surface; SQLite inside the process is enough at project scale |
| Embeddings in canonical tables | Would enter undo, activity, packages and migrations; the index must stay disposable |
| Runtime-loaded SQLite extension | Would let a hostile file or DLL extend SQLite; `sqlite-vec` is compiled in and registered per connection |
| Multi-agent frameworks (LangGraph, CrewAI, AutoGen) | Multiplies latency and memory on a 1B model; deterministic validators do the checking |
| LLM reranker | Extra model calls per request with no measured benefit yet |
| Exposing every registry operation automatically | Internal, file-path, lifecycle and approval operations must never reach the model; exposure is explicit metadata |
