## How to read and update this file

Status words, in order:

| Status | Meaning |
|---|---|
| Specified | The requirement is written down. Nothing, or only part, is built. |
| Designed | Data, operations, screens and tests are planned in a written contract. |
| Built | The code exists and passes its own tests. |
| Reachable | A normal user can find and use it in the product. |
| Verified | Saving, undo, recovery, permissions, export and re-import, restart, failure cases and end-to-end tests are proven. |
| Release-ready | Performance, security, accessibility, installer, migration and documentation checks all pass. |

Proof levels ([ADR-0030](../adr/ADR-0030-verification-ladder-and-release-flow.md)), in the **Proof** column:

| Proof | Meaning | Evidence the checker asks for |
|---|---|---|
| none | No proof claimed. Only Specified and Designed rows. | None. |
| 1 | Built: the code exists. | Tests are named. |
| 2 | Proved on development: unit, integration and end-to-end tests pass on the debug build. | Tests name an end-to-end test (`J:`, `R:` or a `.test.mjs` spec). |
| 3 | Proved on the artifact: the same end-to-end scenarios pass on the release build. | `3 (ev: docs/release/evidence/<file>)`, and the file exists. |
| 4 | Proved on a clean computer with no developer tools. | As level 3. |
| 5 | Proved by people: the team used it and the findings were fixed and checked again. | As level 3. |

"Verified" needs proof level 2 or higher until the Windows track reaches phase W9, then level 3 or higher
(`VERIFIED_MIN_PROOF` in `scripts/lib/feature-status.mjs`).

Importance words: **Must ship** (needed for the first release), **Should ship** (remove from every listing if it slips), **Can wait**, **Removed**.

Rules:

1. A feature moves up only with evidence (a test name, an end-to-end spec, a file path) recorded in the pull request.
2. A feature is not Release-ready while any required cell is empty: screen, AI decision, search decision, tests, export.
3. The **Key** column is a stable lookup key used by scripts and old notes. Wording may change; keys do not. Use the feature name when you talk about a feature.
4. "What exists today" states what was checked in the repository, with a date or a file reference. Claims copied from a README or an audit without a check are not allowed; `scripts/check-feature-status.mjs` refuses them.
5. **How a user reaches it** names a screen route, or `none: <reason>` for backend, process, release, platform or packaging work, or `pending`. **Tests** names tests or says `pending`. `scripts/check-feature-status.mjs` (CI job `governance`) fails when a row lacks its area, screen, tests or status, when a Built row has no tests, when a Reachable row has no screen, or when the **Proof** cell is missing, below what the status needs, or without its evidence. Each section names its specification sources on a `Source:` line.
6. Test reference shorthand: `file.rs::name` is an integration test in `crates/*/tests/`; `(unit)` is a test inside the named source file; `*.test.ts(x)` is a Vitest file under `apps/desktop/src`; `J:` and `R:` are titles in `tests/e2e/specs/01-journey.test.mjs` and `02-restart.test.mjs`. Baseline run: `docs/release/evidence/M0/INDEX.md`.
7. Progress counts come from `node scripts/plan-status.mjs` (checklist) and `node scripts/check-feature-status.mjs` (status totals).
